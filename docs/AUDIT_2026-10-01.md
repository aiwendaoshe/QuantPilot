## 1. P0 —— 必修（影响结果与可用性，建议优先修）

### PID-01 回测「持仓天数」按自然日算，短线结论被系统性扭曲
**位置**：`strategy/backtest.ts:15-21`（`toDays`/`dayDiff`）、`:98`、`:113`

```ts
} else if (dayDiff(pos.entryDate, date) >= holdDays) {   // ← 自然日差
```
`holdDays = 5` 时，`dayDiff` 走 `Date.UTC` 自然日：跨一个周末就只剩 3 个交易日。所有依赖 `holdDays`（默认 5、用户可调）的回测收益/胜率/夏普都会偏离真实短线口径，且用户无从察觉。

**修法**（低风险）：把 `dayDiff` 换成「交易日索引差」——回测器已构造 `allDates`，用 `allDates.indexOf(date) - allDates.indexOf(entryDate) >= holdDays` 或预建 `dateIndex: Map<string,number>`；同时把 `Trade.holdingDays` 语义改为交易日并在 UI 改标签为「交易日」。
**回归验证**：同一份 mock 池，改前后 `totalTrades` 应当变化且大回测区间（如 2023-01-01~2024-12-31）的笔数应增加。

### PID-02 选股把整池结构化克隆传给 Worker，全市场档会爆内存/巨慢
**位置**：`src/main/services/computeService.ts:75`（`worker.postMessage({...req})`）、`src/main/services/strategyService.ts:54-57`、`src/main/services/dataService.ts:231-267`

全市场档：`POOL_HARD_CAP=5400` × `SCREEN_BARS=320` ≈ **173 万个 DailyBar 对象**（约 9 字段/对象）经 postMessage 结构化克隆，序列化 + 反序列化峰值内存常达 0.5~1.5GB，前几版「选股几十秒」在这个档位会退化为分钟级卡顿甚至 OOM。回测池更重。

**修法（推荐三选一，性价比排序）**：
1. **Worker 直连 SQLite**：worker 是 node worker_thread，可直接 `createRequire` 加载 better-sqlite3 读同一份 `quantpilot.db`，主进程只传 `{kind, limit, recentBars, asOf, topN, configs}`，完全绕开克隆。改动最小、收益最大。
2. 主进程把池序列化进 `SharedArrayBuffer` + `Atomics` 传句柄（需 worker 侧解码，复杂度中）。
3. 至少改成**分片 postMessage**（每 500 只一片，边算边收），避免单条消息巨块——但不解决总量。

**回归验证**：5400 只档选股，Node 侧 `--max-old-space-size` 不爆、worker maxRSS 有界、单次数秒级。

### PID-03 个股详情信号用默认策略参数，与仪表盘/回测口径不一致
**位置**：`src/main/services/strategyService.ts:120`

```ts
for (const strat of allStrategies()) { ... }   // 只看默认配置
```
用户在「策略配置」页把均线周期改了、关了某个策略，仪表盘与回测都会用新配置，唯独个股 K 线图上的 pin 仍按默认参数算 → 同一个人在同一个界面上看到两套结论，是最伤可信度的不一致。

**修法**：改用同一个 `buildStrategies()`（已存在，只是定义在同文件第 24 行）；顺带把它导出复用。

## 2. P1 —— 应修（正确性 / 竞态 / 性能 / 交付一致性）

| # | 问题 | 位置 | 影响 | 修法 |
|---|---|---|---|---|
| PID-04 | SQLite 双进程写锁：Node（`dataService`）与 Python 抓取器（`baostock_fetcher.py`）同时写 `quantpilot.db`，双方都**没设 `busy_timeout`** | `dataService.ts:66-69`、`python/baostock_fetcher.py:53-56` | 全市场回填几分钟里，用户点「重新选股 / A股行情」可能直接 `database is locked` 抛错 | 两边加 `PRAGMA busy_timeout=15000`；`lastUpdate`/`dataSource` 只由 Python 独家写，Node 只读不写（避免 meta 表互相覆盖） |
| PID-05 | 拉取/选股无并发锁 | `dataService.pullHistory` / `strategyService.runScreener`、`tray.ts:118-138` 托盘菜单入口无 loading 态 | 托盘菜单连点两次 = spawn 两个 python 同时写库；两个 Worker 同时跑 | 模块级 `busy` 标记 + `Promise` 复用；托盘菜单点击前查锁，锁住时给托盘气泡提示"正在拉取中" |
| PID-06 | 同一只票被多策略命中会出多张卡（`:key = code+date+strategyId`） | `strategyWorker.ts:19-26`、`Dashboard.vue:203-206` | TOP20 里出现 3 张同一只票，观感像 bug | 按 `(code,date)` 聚合成一条（保留最高分 + 命中的策略列表），或明确在卡片角标注「+N 策略」 |
| PID-07 | `getScreeningPool`/`getPool` 逐只查 K 线 | `dataService.ts:235-266` | 5400 次单只 SELECT + 前置 `IN (SELECT DISTINCT code FROM daily)`，启动成本高 | 一条 JOIN 全量取出在内存分组；或建覆盖索引后一次 `ORDER BY code, date DESC LIMIT` 流式分组 |
| PID-08 | 详情 marks 计算 O(n²) 且每根 bar 都 `slice` + 全量跑 generateSignal | `strategyService.ts:118-133` | 240 根 × 7 策略 = 1680 次完整信号计算 + 大量数组复制，打开个股页有肉眼可见延迟 | 每 3~5 根算一次并缓存上次结果（信号只在条件成立时出现），或把窗口首日和末日之间做增量状态机 |

| PID-10 | pending 买入门槛不足时静默丢弃 | `backtest.ts:64-77` | `cash<=0` / `qty=0`（价格过高、资金不够一手）时不成交也不记任何日志/交易，资金曲线会莫名不动 | 不成交时写 warn 日志（或记一笔 rejected 计数），别让结果"看起来像策略没信号" |
| PID-11 | 图表 `watch(..., {deep:true})` 深度监听 240 根 K 线 + marks | `KLineChart.vue:24`、`ScoreRadar.vue:23`、`EquityChart.vue:23` | 每次更新遍历整棵对象树，切换/刷新时白烧 CPU | 去掉 `deep`（引用变化本身就够触发重算） |
| PID-12 | 回测未校验 `startDate <= endDate`、不校验未来日期 | `Backtest.vue:31-34` | 区间反了/选到未来 → 空结果，用户以为是策略没信号 | 加边界校验 + 友好错误提示；`endDate` 不许超过库内 `barTo` |
| PID-13 | `Trade.pnlPct` 未计滑点，但资金结算计了滑点 | `backtest.ts:104` | 成交明细"收益%"与期末资金/曲线对不上，懂行的主子一看就觉得算错 | `pnlPct` 里也扣 `2*slippage`，或与 UI 文案统一标注「未计滑点」 |
| PID-14 | 交付物缺失：`release/QuantPilot-Setup-0.5.3.exe` **无 .blockmap** | `release/` | 0.4.x~0.5.2 都有 blockmap，0.5.3 没有 → 安装包后续差分更新退化 | 确认 `dist:win` 收尾产物完整；跑一次干净打包复核 |
| PID-15 | README 版本号漂移 | `README.md:83` 仍写「产出 0.5.0.exe」 | 文档与事实不符 | 引入 `scripts/bump.mjs`（记忆里 labreg 项目有先例）：一处改版本自动同步 `package.json` + README + 窗口抬头 + 不同名不覆盖 |

## 3. P2 —— 可选优化（可按节奏排）

**工程化 / 交付**
1. `.gitignore` 漏：`tsconfig.*.tsbuildinfo`、`_smoke/out/`、`data/preview/`、`data/reports/` → 会把构建产物/截图/离线预览页带进版本库。
2. `_smoke/` 里 `shot.py`、`test_market.ts`、`test_marks.ts`、`e2.log` 等验证脚本仍在（约定是"验完即删"）。建议要么删，要么归入 `scripts/` 并加 README 说明。
3. 无 `LICENSE`（`package.json` 已声明 MIT）、无 CI、无一键 `verify`（建议 `verify = typecheck + build:worker + 冒烟` 一条命令）。
4. SQLite schema 无 `PRAGMA user_version` 迁移机制。现在加列还能靠 `CREATE IF NOT EXISTS` 糊过去，一旦库里有几百 MB 真实数据就难改了。**越早加越好**。
5. 前端存在两套「信号类型→中文」映射：`src/shared/constants/strategies.ts:45 SIGNAL_TYPE_LABELS` 与 `StrategyConfig.vue:13-18 typeLabel`；About/StockDetail 里也各有一份硬编码列表。全部收敛到 shared 常量。

**性能 / 架构**
6. Worker 每次 `new Worker` + `terminate`，无复用：建议长驻一个常驻 worker，按 `id` 做请求-响应配对（配合 PID-02 的数据传递改造一起做）。
7. `strategy/` 与 `src/` 双轨引用：`strategy/*.ts` 用相对路径 `../src/shared/types/...`，而 src 内部统一 `@shared` 别名。建议统一（把 `strategy/` 迁进 `src/strategy` 或给 `tsconfig.worker.json` 加 paths 映射后全用别名）。
8. `strategy/demo.ts`、`phase2-demo.ts`、`phase4-worker-test.ts` 是开发脚本却混在产品目录（被 `tsconfig.node.json` 的 include 覆盖、参与主进程 typecheck）。建议移 `scripts/`。
9. 选股核心循环在两处重复实现：`strategyWorker.handleScreener` 与 `strategyService.runScreener` 的兜底分支（同一段双层 for）。抽 `runScreenerCore()` 放 `strategy/` 供两边调用，避免以后改一个忘另一个。
10. 注释偏长：`dataService.ts` 单文件 589 行里约 100 行是踩坑注释。建议把"史"收敛进 `docs/` 或 CHANGELOG，代码内只留一句要点（保留风险提示，删叙事）。

**算法 / 数据口径**
11. `annualizedVolatility` 在样本不足时返回 0 → `scoring.ts:57` 波动因子稳拿 100 分，新上市/短样本股票评分虚高。建议返回中性分或按样本比例打折。
12. `isLimitUp/isLimitDown` 统一按 9.5% 判定（`indicators.ts:173-193`）：创业板/科创板是 20%、ST 是 5% → 判定会错。建议按 `meta.market`（`sz.3`/`sh.6`?）与名称含 ST 动态取阈值（注意：DailyBar 里没有 market 字段，需要 `StockMeta` 入参）。
13. `resample()` 的周线 `preClose = chunk[0].preClose`（`indicators.ts:243`）：语义上是周首前一日收盘，直接用日 preClose 会让周线级别的涨停/反包判定失准。若有策略用 resample，需复核。
14. `mockData`：数据源标记（演示/真实）做得很好，是加分项，继续保持——这是"诚实数据"的正面范例。

**交互 / 安全**
15. 桌面通知文案缺代码：`schedulerService.ts:67` `"TOP1: ${name}(${score})"`，与项目铁律「代码后紧跟中文名」不符；且 `Notification` 未接 `on('click')`，点了没反应。
16. Dashboard「检测环境」把结果写进 `pullMessage`（`stockStore.ts:158`），语义是"拉取消息位" → 建议独立的通知/toast 通道。
17. 无全局 toast / 错误提示机制，各处各自 `v-if` 分支。
18. `sandbox: false`（`main.ts:34`、`about.ts:57`）：preload 只用了 `contextBridge`/`ipcRenderer`，可以开 `sandbox: true`；顺带补 `app.setAppUserModelId()`（Windows 托盘/通知分组）。
19. IPC 入参无边界校验（`universe` 负数/超大、`code` 任意串）：目前全是 prepared statement，无注入风险，但建议加最小校验（zod 或手写几行）。
20. 死代码：`tray.ts:87 sendNavigate`、`chartOptions.ts:16 C.ma60`、`strategy/report.ts` 的 `writeJsonReport`（仅 demo 调用）。

## 4. 做得好的（别改坏）

- **杜绝未来函数**：信号喂进 `date <= asOf` 的切片，回测 T+1 次日开盘成交、个股数据末根强制平仓（`endOfData`）——这两条是量化软件最容易翻车的地方，本项目做对了。
- **数据诚实化**：`dataSource` 落库 + 前端状态条显式标「演示数据/真实行情」，拉取失败时宁可报错也拒绝用 mock 覆盖真实库——比"假装成功"强太多。
- **Python 探测三原则**（穷举候选 + 按退出码判定 + 异步 exec）已作为铁律写进注释，`findPython` 的候选清单还能在 UI 里回显诊断，排障体验很好。
- **看门狗用"空闲超时"而非总超时**：正确区分"慢"与"卡死"，并且错误文案写"服务端无响应"而非裸退出码。
- **关于窗模态 + `meta.fullscreen` 隐藏 header**：用路由元信息解决共用 index.html 的问题，干净。
- **策略层与 Electron 完全解耦**：`strategy/` 能脱离 Electron 用 tsx 直接跑，测试与复用成本低。
- **`purge_non_targets` 只删非目标行**：即使中途被杀也不会一次性抹掉已有数据，是很稳的取舍。

### A 批实施预案（逐项，含改法要点与回归验证）

### 9.2 PID-13 复核结论（推翻原审计意见）

原建议「`pnlPct` 再扣 `2*slippage`」经实测**会造成 60 倍误差，不采纳**：

```
entry=10.01 exit=10.989
  现网公式  (exit-entry)/entry - 2c        = 9.7202%   资金实际口径 = 9.7144%  → 差 0.006%
  审计建议  现网公式 - 2*slippage          = 9.3202%   偏离资金实际 0.394%
```

原因：`entryPrice`/`exitPrice` 本身已含滑点（`open*(1+s)` / `*(1-s)`），
双边滑点天然体现在分子两端，再减一次即重复扣。**保留原公式**，仅在注释与表头 title 声明口径。
后续若再引用 PID-13，请以本节结论为准。

### 18.2 本轮修复的重大工程缺陷（P0 级）

**worker 静默打老产物**：`dist:win = vite build && electron-builder`，而 `vite build` **只编 renderer+main+preload，从不跑 worker 的 tsc emit**（worker 由 `tsconfig.worker.json` 产出到 `dist-electron/`）。即 **worker 产物靠上次残留，所有改 worker/strategy 的代码都进不了安装包**。实测曾发现 `strategyWorker.js` 时间戳停留在 3 天前。
- **影响面**：不止 M3——历史上所有改 worker 的改动都可能在打陈旧包。
- **修复**：`build = vite build && tsc -p tsconfig.worker.json`。
- **新增铁律**：改 worker/strategy 后必须核对 `dist-electron/src/main/workers/strategyWorker.js` 时间戳，不能只看 main.js（新）就以为全打包了。
